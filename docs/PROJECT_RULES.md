# TeamTrack — Project Rules

## 1. Назначение проекта

TeamTrack — внутренняя рабочая система университетской проектной команды примерно из 15 человек.

Основная задача:

> Собрать поиск конкурсов и управление участием команды в одной системе.

TeamTrack объединяет:

- поиск конкурсов;
- гранты;
- хакатоны;
- турниры;
- олимпиады;
- форумы;
- акселераторы;
- чемпионаты;
- другие мероприятия;
- проекты;
- участников команды;
- задачи;
- дедлайны;
- документы;
- комментарии;
- результаты;
- статистику.

---

## 2. Главный принцип

TeamTrack не должен превращаться в набор независимых функций.

Все основные сущности должны быть связаны.

Основной цикл:

Конкурс
↓
Решение участвовать
↓
Проект
↓
Команда
↓
Задачи
↓
Работа
↓
Дедлайн
↓
Подача заявки
↓
Результат
↓
История
↓
Аналитика

---

Первым приоритетом является система поиска и каталогизации мероприятий.

До реализации большого количества дополнительных функций необходимо получить работающий pipeline:

Источник
↓
Получение данных
↓
Парсинг
↓
Нормализация
↓
Валидация
↓
Удаление дублей
↓
Сохранение в PostgreSQL
↓
Backend API
↓
Flutter
↓
Каталог конкурсов

---

## 4. Первый продуктовый результат

Первой значимой рабочей версией должна быть система Competition Discovery.

Она должна позволять:

- автоматически получать мероприятия из внешних источников;
- сохранять их в БД;
- обновлять существующие записи;
- предотвращать дубли;
- отображать мероприятия в приложении;
- искать мероприятия;
- фильтровать мероприятия;
- открывать карточку мероприятия;
- переходить на официальный сайт.

---

## 5. Категории мероприятий

Система должна поддерживать минимум:

competition
grant
hackathon
tournament
olympiad
forum
accelerator
championship
other

В пользовательском интерфейсе отображаются понятные русские названия.

Внутри системы используются стабильные enum/code значения.

---

## 6. Источники мероприятий

TeamTrack должен поддерживать несколько внешних источников.

Каждый источник является независимым.

Например:

Source A
Source B
Source C
Source D

Проблема одного источника не должна останавливать обработку остальных.

---

## 7. Добавление нового источника

Добавление нового источника не должно требовать переписывания существующих scraper-модулей.

Архитектура должна позволять:

Scraper Engine
├── Source Adapter A
├── Source Adapter B
├── Source Adapter C
└── Source Adapter N

Новый источник добавляется отдельным адаптером.

---

## 8. Данные конкурса

Минимальная сущность Competition должна поддерживать:

- id
- title
- organizer
- type
- official_url
- source_url
- start_at
- deadline_at
- result_at
- prize_fund
- region
- format
- audience
- topics
- requirements
- description
- status
- source_id
- created_at
- updated_at

Дополнительные поля могут добавляться только при реальной необходимости.

Не создавать десятки полей «на будущее».

---

## 9. Источник и официальный сайт

Не путать:

source_url

и:

official_url

source_url — страница, с которой была получена информация.

official_url — официальная страница самого мероприятия.

Если официальный URL неизвестен:

official_url = NULL

Нельзя придумывать URL.

---

## 10. Данные нельзя выдумывать

Если источник не содержит информацию, использовать NULL или другое заранее определённое отсутствие значения.

Нельзя самостоятельно придумывать:

- призовой фонд;
- дедлайн;
- организатора;
- регион;
- требования;
- дату результатов;
- официальный сайт.

---

## 11. Нормализация

Все внешние источники должны приводиться к единому внутреннему формату.

Например:

Хакатон
Hackathon
IT Hack
Студенческий хакатон

могут соответствовать:

hackathon

Нормализация должна быть предсказуемой.

Не использовать AI для нормализации на первой версии.

---

## 12. Дедлайн

Дата и время дедлайна должны храниться корректно.

Backend отвечает за вычисление deadline status:

green
yellow
orange
red
gray
blue

Flutter не вычисляет deadline status самостоятельно.

---

## 13. Актуальность конкурсов

Система должна учитывать, что информация на внешних сайтах изменяется.

При повторном сборе:

Новая запись
→ CREATE

Существующая запись + данные изменились
→ UPDATE

Существующая запись + данные не изменились
→ SKIP

Особенно важны изменения:

- deadline;
- start date;
- status;
- prize fund;
- official URL;
- description.

---

## 14. Дубликаты

Один конкурс может находиться на нескольких сайтах.

TeamTrack не должен создавать несколько одинаковых мероприятий без причины.

Для определения дублей можно использовать комбинацию:

- external_id;
- official_url;
- source_url;
- normalized title;
- organizer;
- dates;
- content hash.

Одно поле не должно автоматически считаться абсолютным доказательством идентичности.

---

## 15. Проекты

Когда команда решает участвовать в мероприятии:

Competition
↓
Project

Проект может быть связан с конкурсом.

Но проект и конкурс — разные сущности.

Competition:

> информация о внешнем мероприятии.

Project:

> внутренняя работа команды по участию в мероприятии.

---

## 16. Задачи

Задачи принадлежат проектам.

Пример:

Проект
├── Изучить положение
├── Определить команду
├── Разработать концепцию
├── Сделать презентацию
├── Написать заявку
├── Подготовить документы
└── Отправить заявку

Каждая задача может иметь:

- название;
- описание;
- ответственного;
- дедлайн;
- приоритет;
- статус;
- комментарий.

---

## 17. Команда

Пользователь может участвовать в нескольких проектах.

Проект может содержать нескольких участников.

Не связывать пользователя напрямую с одним проектом.

Использовать отдельную связь:

project_members

---

## 18. Результаты

Завершённый проект не удаляется.

Он переходит в историю.

Поддерживаются:

winner
first_place
second_place
third_place
finalist
participation
rejected

Результат должен сохраняться отдельно от текущего статуса проекта.

---

## 19. История

История команды должна строиться на реальных завершённых проектах.

Нельзя хранить статистику только в виде вручную изменяемых чисел.

Например:

84 участия
32 финала
17 побед

должны вычисляться из данных системы.

---

## 20. Аналитика

Первая версия аналитики не использует AI.

Используются обычные SQL-запросы и вычисления backend.

Примеры:

- количество проектов;
- количество участий;
- количество побед;
- количество финалов;
- количество грантов;
- сумма призовых;
- количество выполненных задач;
- количество просроченных задач;
- процент побед.

---

## 21. AI

AI НЕ используется в первой версии.

Не использовать AI для:

- поиска конкурсов;
- парсинга;
- нормализации;
- дедупликации;
- аналитики;
- управления задачами.

AI будет отдельным будущим слоем.

Архитектура должна позволять добавить AI позднее без переписывания основной системы.

## 33. Что запрещено реализовывать заранее

- AI;
- web-версию;
- сложную систему рекомендаций;
- микросервисную архитектуру;
- распределённые очереди;
- Kubernetes;
- сложную event-driven архитектуру;
- сложный search engine;
- Elasticsearch;
- Kafka;
- Redis, если он не нужен текущей задаче;
- дополнительные внешние сервисы;

---

## 34. Правило минимальной архитектуры

TeamTrack должен использовать:

> минимально достаточную архитектуру.

Не нужно строить инфраструктуру уровня крупной корпорации для команды из примерно 15 человек.

При этом нельзя жертвовать:

- безопасностью;
- целостностью данных;
- расширяемостью;
- тестируемостью.

---

## 35. Размер проекта

TeamTrack должен оставаться понятным небольшому разработчику или команде.

Любое архитектурное решение должно отвечать вопросу:

> Упростит ли это дальнейшую разработку?

Если нет — решение требует дополнительного обоснования.

---

## 36. Производительность

Приоритет:

Correctness
>
Security
>
Maintainability
>
Performance optimization

Не оптимизировать то, что ещё не является проблемой.

Сначала сделать правильную работающую реализацию.

---

## 37. Надёжность scraper

Scraper должен корректно переживать:

- недоступность сайта;
- timeout;
- HTTP errors;
- изменение HTML;
- отсутствие отдельных полей;
- временные ошибки;
- rate limiting.

Один источник не должен ломать весь процесс.

---

## 38. Юридические ограничения scraper

Перед подключением источника необходимо учитывать:

- robots.txt;
- правила сайта;
- условия использования;
- ограничения частоты запросов.

Не использовать агрессивный scraping.

Не обходить технические ограничения сайта.

---

## 39. Источники

Каждый источник должен иметь:

- id;
- name;
- base_url;
- enabled;
- last_checked_at;
- last_success_at;
- last_error;
- items_found.

Администратор должен иметь возможность отключить источник.

---

## 40. Обработка ошибок

Ошибки scraper должны сохраняться в логах.

Например:

Source A → ERROR
Source B → SUCCESS
Source C → SUCCESS

Ошибка одного источника не должна приводить к:

Entire scraper → FAILED

---

## 41. UX

Интерфейс должен быть:

- простым;
- современным;
- понятным;
- быстрым;
- ориентированным на рабочий процесс команды.

Не использовать декоративные элементы без функциональной пользы.

---

My tasks

Раздел «Срочно» показывает:

- просроченные проекты;
- просроченные задачи.

---

## 44. Mobile First

Основной клиент:

Flutter
iOS
Android

Интерфейс должен проектироваться прежде всего для мобильного использования.

---

## 45. Backend First Principle

Для критически важных бизнес-правил:

> Backend = source of truth

Flutter не должен самостоятельно определять:

- permissions;
- deadline status;
- права пользователя;
- критические бизнес-правила.

---

## 46. Безопасность

Безопасность является обязательной частью функциональности.

Нельзя считать функцию готовой, если она работает, но позволяет:

- IDOR;
- обход permissions;
- получение чужих файлов;
- получение чужих проектов;
- получение чужих задач;
- утечку токенов;
- SQL injection.

---

## 47. Готовность функции

Функция считается завершённой только если в необходимом для текущего этапа объёме реализованы:

- Code;
- Database;
- API;
- UI;
- Validation;
- Error handling;
- Tests.

Не требуется создавать всё это одновременно для каждого маленького изменения, если текущий этап не предполагает соответствующий слой.

---

## 48. Definition of Done

Перед завершением этапа необходимо проверить:

[ ] Код компилируется

[ ] Тесты проходят

[ ] Нет очевидных ошибок

[ ] Нет секретов в Git

[ ] API работает

[ ] Database работает

[ ] UI работает

[ ] Error states обработаны

[ ] Permissions проверяются backend

[ ] Документация обновлена

---

## 49. Главное правило продукта

TeamTrack должен отвечать на вопрос:

> «Что нам нужно сделать, чтобы успешно участвовать в этом мероприятии?»

Пользователь должен видеть:

- Что?
- Когда?
- Кто?
- Что осталось?
- Что просрочено?
- Какой результат?

---

## 50. Финальный принцип

TeamTrack не должен быть:

ещё одним списком конкурсов

и не должен быть:

ещё одним таск-менеджером.

TeamTrack должен быть:

> ЕДИНОЙ СИСТЕМОЙ УЧАСТИЯ КОМАНДЫ В КОНКУРСАХ И ПРОЕКТАХ.

Каждая новая функция должна усиливать эту цель.

---

## 51. Правило поэтапной разработки

Разработка должна происходить маленькими завершёнными этапами.

Нельзя одновременно создавать:

- backend;
- database;
- Flutter;
- scraper;
- authentication;
- notifications;
- analytics

без необходимости.

Каждый этап должен иметь одну конкретную цель.

Пример:

Этап 1:
Создать структуру backend.

Этап 2:
Подключить PostgreSQL.

Этап 3:
Создать таблицу competitions.

Этап 4:
Создать sqlc queries.

Этап 5:
Создать Competition repository.

Этап 6:
Создать Competition service.

Этап 7:
Создать Competition API.

Этап 8:
Проверить API.

Только после успешной проверки переходить дальше.

---

## 52. Правило STOP

Если задача текущего этапа выполнена, AI должен остановиться.

AI НЕ должен самостоятельно переходить к следующему этапу.

После завершения этапа AI должен сообщить:

1. Что было сделано.
2. Какие файлы изменены.
3. Что проверить.
4. Какие команды выполнить.
5. Есть ли известные проблемы.
6. Какой следующий этап предлагается.

После этого необходимо ждать дальнейшей команды пользователя.

---

## 53. Правило изменения существующего кода

Перед изменением существующего кода AI обязан:

1. Прочитать AGENTS.md.
2. Прочитать PROJECT_RULES.md.
3. Изучить текущую структуру проекта.
4. Найти связанные файлы.
5. Проверить зависимости.
6. Определить минимальное изменение.
7. Только после этого изменять код.

Нельзя переписывать рабочую систему без причины.

---

## 54. Правило новых файлов

Новый файл можно создавать только если он действительно нужен.

Перед созданием нового файла AI должен понимать:

- зачем он нужен;
- к какому модулю относится;
- почему существующий файл не подходит;
- какую ответственность он содержит.

Не создавать файлы только ради формального разделения кода.

---

## 55. Правило размера файлов

Если файл становится слишком большим или содержит несколько независимых ответственностей, его необходимо разделить.

Но нельзя дробить код искусственно.

Цель:

> небольшие понятные модули с одной ответственностью.

Не создавать десятки файлов для простейшей функции.

---

## 56. Запрет на преждевременную абстракцию

Не создавать абстракции только потому, что они могут понадобиться в будущем.

Сначала должна появиться реальная необходимость.

Запрещено создавать:

- универсальные фабрики без использования;
- абстракции ради абстракций;
- дополнительные слои без ответственности;
- generic helpers без повторяющегося использования;
- сложные паттерны ради демонстрации архитектуры.

---

## 57. Правило YAGNI

Использовать принцип:

> You Aren't Gonna Need It.

Не реализовывать функциональность, которая не нужна текущему этапу.

Если функция нужна в будущем, достаточно правильно заложить расширяемую точку интеграции.

Саму будущую функцию сейчас создавать не нужно.

---

## 58. Правило реального кода

Если текущий этап требует реальной реализации, нельзя заменять её:

- mock;
- fake;
- hardcoded JSON;
- временными заглушками;
- фиктивными данными.

Допускаются mock/fake только в тестах или если текущий этап явно посвящён прототипированию.

---

## 59. Правило объяснения решений

Если AI хочет использовать технологию, библиотеку или архитектурный подход, которых нет в утверждённом стеке, он должен сначала объяснить:

1. зачем это нужно;
2. какую проблему решает;
3. почему существующего стека недостаточно;
4. какие минусы;
5. как это повлияет на проект.

Без согласования нельзя добавлять новые ключевые технологии.

---

## 60. Главный критерий качества

Хороший TeamTrack — это не максимально большое количество кода.

Хороший TeamTrack — это:

> минимальное количество необходимого кода, которое надёжно решает реальную задачу команды.

Не количество файлов и строк кода является целью.

Цель — работающая, безопасная и понятная система.
